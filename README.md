# AI-детектив — лабораторная работа 6

Исследование ответов одной LLM на вопросы по вымышленному досье. Сравниваются полный контекст (A), BM25 top-15 (B) и те же 15 утверждений, сгруппированные по p-adic ветвям (C).

## Участники

| Участник | Ответственность |
|---|---|
| Дедкова А. В. | Досье, утверждения, вопросы и эталоны |
| Генне К. В. | BM25, p-adic организация, контекст и стресс-кейсы |
| Маракулин А. А. | LLM, Streamlit, метрики, интеграция и тесты |

Все участники должны проверить эталоны и понимать архитектуру целиком.

## Данные и режимы

`data/` содержит 10 документов (более 5 000 слов), 37 атомарных утверждений, 12 вопросов и 28 подготовленных стресс-кейсов: 12 перестановок, 4 удаления посылки и 12 добавлений противоречия. Для каждого кейса зафиксирован ожидаемый статус. `src/data_io.py` проверяет уникальность ID, ссылки и дословное вхождение `evidence` в документ.

- **A** передаёт все документы в исходном порядке и реестр утверждений с ID, чтобы модель могла сослаться на доказательства.
- **B** выбирает не более 15 утверждений BM25.
- **C** использует тот же набор ID, группирует по пути `[a₀,a₁,a₂]` при `p=3` и сортирует события по времени внутри ветви.

В стресс-кейсе меняется один фактор. Перестановка документов использует seed 42. Удаление убирает утверждение из реестра и его дословный фрагмент из документа. Добавление противоречия добавляет новый документ и новое утверждение. Каждый запрос сохраняет полный текст фактически переданного контекста и состав документов и утверждений.

## Установка

Требуется Python 3.11+ и доступ к Groq API для реального эксперимента. Выбранная модель и формат строгого JSON описаны в [документации Groq](https://console.groq.com/docs/model/qwen/qwen3.8-27b) и [Structured Outputs](https://console.groq.com/docs/structured-outputs).

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest -q
```

Сервисный ключ можно задать в окружении, в скрытом поле Streamlit или через `--ask-key`. Его не следует сохранять в репозитории:

```bash
export GROQ_API_KEY='ваш ключ'
```

По умолчанию используется `qwen/qwen3.8-27b`; модель можно указать в интерфейсе или через `--model`. API вызывается с одним сохранённым промптом из `prompts/system.txt`, одной моделью и одинаковыми параметрами для всех режимов. Ответ запрашивается в JSON Schema и затем проверяется локально. Ключ в файлы результатов не записывается; необработанный ответ сохраняется для ручного анализа.

## Интерфейс и полный эксперимент

```bash
.venv/bin/streamlit run app.py
```

В интерфейсе можно загрузить четыре JSONL файла, ввести Groq API key в скрытое поле, выбрать вопрос, режим, подготовленный стресс-кейс, увидеть контекст, p-adic ветви, ответ, уверенность, доказательства и метрики сохранённых результатов. Прогон всех режимов делает 120 запросов: 36 исходных и 84 стрессовых; можно выбрать часть режимов. Каждый ответ сразу добавляется в `results/runs.jsonl`; файл исключён из Git.

Запуск без интерфейса:

```bash
.venv/bin/python run_experiment.py --model qwen/qwen3.8-27b
```

Для скрытого ввода ключа без переменной окружения добавьте `--ask-key` в терминале. Для быстрой проверки исходных 36 ответов добавьте `--baseline-only`. Невалидный ответ модели сохраняется с исходным JSON и учитывается как ошибка в общей точности статуса. Ошибку доступа к API можно повторить с тем же `run_id`; уже полученные ответы, включая невалидные, не запрашиваются повторно. Запуск без `--run-id` получает новый идентификатор; результаты разных прогонов не смешиваются.

Если аккаунт пока не пропускает длинный запрос A, можно выполнить B/C отдельно и затем добавить A к тому же прогону:

```bash
.venv/bin/python run_experiment.py --ask-key --modes B C
.venv/bin/python run_experiment.py --ask-key --modes A --run-id RUN_ID
```

У предоставленного ключа при проверке лимит составлял 7 000 входных токенов в минуту, а запрос A занял 10 593 токена. В таком состоянии Groq отклоняет A до генерации; для честного режима A нужен более высокий лимит аккаунта. Разбиение документов на несколько запросов изменило бы сравниваемый режим.

Реальный прогон B/C для выбранной модели завершён; измеренные частичные результаты находятся в `BC_RESULTS.md`. Полные ответы и контексты остались в локальном `results/runs.jsonl` и не включены в Git.

## Отчёт

После **полного успешного реального** прогона возьмите напечатанный `run_id` и создайте PDF:

```bash
.venv/bin/python generate_report.py --run-id RUN_ID --output report.pdf
```

Генератор отказывается строить отчёт по неполному прогону, ошибкам API или тестовой модели. В отчёте приведены метрики A/B/C, устойчивость к трём стресс-тестам, уверенность при недостатке данных, ограничения эксперимента и вклад участников. Итоговые интерпретации и эталоны следует проверить всей командой до сдачи. `report.pdf` создаётся только после реального прогона; в репозиторий не включены придуманные результаты.
